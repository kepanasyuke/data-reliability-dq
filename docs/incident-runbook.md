# Runbook: обработка инцидентов DQ

Документ для дежурного. Формат: симптом → диагностика → решение → постмортем.
Проверки названы по `check_id` из `checks/dq_checks.json`.

## Общие правила

1. Никаких изменений в mart-слое до того, как зафиксирован масштаб: сколько
   строк, какие клиенты, какие дашборды затронуты. Скриншот отчёта +
   `sample_sql` из инцидента прикладываются в тикет.
2. Перезаливка партиции — только после остановки DAG'а, который её пишет,
   иначе получится дубликат гранулярности (см. `turnover.duplicate_grain`).
3. Инцидент закрывается не после перезаливки, а после зелёного прогона
   `python run.py run`. Автозакрытие фиксирует `run_id` в `resolution_note`.
4. Если инцидент повторяется третий раз за неделю — это не инцидент, а дефект
   процесса загрузки: нужен тикет в команду ETL, а не новый перезалив.

Быстрая проверка состояния:

```bash
python run.py status            # открытые инциденты, MTTR, нарушения SLA
python run.py report            # что именно упало в последнем прогоне
```

В кластере:

```sql
-- что приехало за последние сутки
SELECT entity, load_dt, rows_loaded, status
  FROM ops.etl_batch
 WHERE load_dt >= now() - interval '2 days'
 ORDER BY load_dt DESC;

-- состояние инцидентов
SELECT incident_id, check_id, severity, status, opened_at, occurrences
  FROM ops.dq_incident
 WHERE status <> 'RESOLVED'
 ORDER BY severity, opened_at;
```

## P1: freshness — загрузка не приехала

**Симптом.** `turnover.freshness` / `loans.freshness` > SLA; дашборд показывает
пустой последний день; потребители пишут в чат «данных нет».

**Диагностика.**

```sql
SELECT * FROM ops.etl_batch WHERE entity = 'fct_account_turnover_daily'
 ORDER BY load_dt DESC LIMIT 5;
```

- `status = 'FAILED'` → смотреть лог таска в Airflow: источник, ресурсная
  очередь, сегмент.
- строки нет вообще → DAG не запускался: проверить `ExternalTaskSensor`
  (родительский DAG `mart_account_turnover_daily`), `sla_miss_callback`,
  доступность планировщика.
- `status = 'SUCCESS'`, но `load_dt` старый → таск упал после записи метаданных:
  проверить, не идемпотентна ли загрузка.

**Решение.** Перезапуск таска (`airflow tasks clear` либо кнопка Rerun) с
`--conf '{"full_refresh": true}'`, если предыдущая попытка успела вставить часть
строк. После успеха — обязательный `ANALYZE` проверяемых таблиц и прогон DQ.

**Постмортем.** Ответить на три вопроса: почему упало, почему узнали от
потребителей (а не от алерта), почему повторный запуск не самовосстановился.

## P1: volume_anomaly — частичная загрузка

**Симптом.** Объём за последний день < 70% медианы предыдущих 7 дней, при этом
свежесть в норме. Самый опасный класс: всё «зелёное», а данных за день нет.

**Диагностика.**

```sql
-- профиль по источникам: где именно потеряли строки
SELECT src_system, dt, COUNT(*) AS rows
  FROM mart.fct_account_turnover_daily
 WHERE dt >= current_date - 3
 GROUP BY src_system, dt
 ORDER BY dt, src_system;

-- сколько счетов пришло за день против обычного
SELECT dt, COUNT(DISTINCT account_id) AS accounts
  FROM mart.fct_account_turnover_daily
 WHERE dt >= current_date - 8
 GROUP BY dt ORDER BY dt;
```

- потеря по одному `src_system` → источник (АБС/CRM) отдал неполный файл;
- потеря равномерная по всем счетам → обрезанный выгрузочный файл или лимит
  строк в коннекторе;
- потеря по части счетов → фильтр в ETL (например, сменился справочник
  отделений).

**Решение.** Перезалить партицию целиком (`DELETE` по `dt` + повторная загрузка),
не «догонять» недостающие строки вставкой поверх: это создаст дубликаты.
Проверить `batch.rowcount_match` после перезаливки.

## P1: orphan_client — сироты по справочнику

**Симптом.** Обороты по `client_id`, которого нет в `dim_client`. Такие строки
молча выпадают из отчётов по клиентам.

**Диагностика.**

```sql
SELECT t.client_id, COUNT(*) AS rows, MIN(t.dt), MAX(t.dt), MIN(t.src_system)
  FROM mart.fct_account_turnover_daily t
  LEFT JOIN mart.dim_client c ON c.client_id = t.client_id
 WHERE t.dt >= current_date - 30 AND c.client_id IS NULL
 GROUP BY t.client_id;
```

- единичный «мусорный» ключ (`CL999999`) → баг ETL или тестовые данные в проде;
- реальные клиенты → справочник грузится позже факта: смотреть порядок тасков
  в DAG. Классика — факт грузится параллельно с dim.

**Решение.** Приоритет: сначала справочник, потом факт; в DAG поставить
зависимость. Если клиент реально новый — догрузить dim и повторить DQ.

## P2: balance_continuity — разрыв остатка

**Симптом.** `balance_eod(dt) ≠ balance_eod(dt-1) + credit − debit`.

**Диагностика.** Взять `sample_sql` из инцидента: там `prev_balance`, обороты и
посчитанная разница. Классы причин:

| Причина | Признак |
| --- | --- |
| пропущен день | разница равна полному обороту за пропущенный день |
| задвоенная строка | разница равна оборотам за день со знаком |
| сдвиг остатка | разница кратна похожей сумме по многим счетам сразу |
| смена валюты | разрыв только по счетам с `currency <> 'RUB'` |

```sql
-- проверка версии "пропущен день"
SELECT account_id, dt, COUNT(*) FROM mart.fct_account_turnover_daily
 WHERE dt BETWEEN current_date - 5 AND current_date
 GROUP BY account_id, dt
 HAVING COUNT(*) = 0;
```

**Решение.** Перезаливка затронутых партиций. Нельзя «подправить» остаток
вручную: он пересчитывается из оборотов, а ручная правка сломает следующий день.

## P2: debt_within_limit — долг выше лимита

**Симптом.** `debt_amt > limit_amt`. Схема валидна, бизнес-инвариант — нет.

**Диагностика.** Проверить, что изменилось: лимит (пересогласование) или долг
(ошибка курса/конвертации).

```sql
SELECT client_id, product_code, month, limit_amt, debt_amt,
       ROUND(debt_amt - limit_amt, 2) AS excess
  FROM mart.fct_loan_portfolio_monthly
 WHERE debt_amt > limit_amt + 0.01
 ORDER BY excess DESC;
```

**Решение.** Если лимит реально снижен — обновить справочник лимитов и
перезалить портфель. Если ошибка расчёта — тикет в команду продукта; DQ-проверку
не отключать, иначе инвариант перестанет существовать.

## P2: segment.completeness / inn.valid / ogrn.valid — справочник клиентов

**Симптом.** Пустой сегмент или неверное контрольное число.

**Диагностика.** Источник справочника (CRM/АБС) отдаёт поле пустым или с другим
форматом. Для ИНН — проверить формат: 10 знаков у ЮЛ, 12 у ИП; 12-значный ИНН,
записанный в поле 10 знаков, всегда даст ошибку контрольного числа.

**Решение.** Исправление в источнике + перезаливка dim. Заполнять сегмент
«на глаз» в mart-слое нельзя: это скрывает проблему в CRM и создаёт два
источника правды.

## P3: rowcount_match — расхождение метаданных

**Симптом.** `rows_loaded` из `ops.etl_batch` не равен фактическому `COUNT(*)`.

**Диагностика.** Обычно одна из причин:

- merge без `DELETE` → строк больше (плюс дубликаты: смотреть
  `turnover.duplicate_grain`);
- загрузка в партицию с последующим `VACUUM`/`REORGANIZE`;
- таск писал в другую партицию (сдвиг даты по часовому поясу).

**Решение.** Не влияет на цифры в дашборде, но ломает доверие к метаданным:
исправить запись `rows_loaded` и добавить проверку часового пояса в ETL.

## Эскалация

| Severity | Реакция | Канал |
| --- | --- | --- |
| P1 | 15 минут, 24/7 | звонок дежурному DRE + чат `#dq-alerts` |
| P2 | 60 минут в рабочие часы | чат + тикет в Jira (project `DQ`) |
| P3 | в течение рабочего дня | тикет в Jira |

Эскалация второго уровня — владелец домена данных (аналитик направления).
Технические причины (падение сегмента, ресурсная очередь) уходят в команду
платформы.
