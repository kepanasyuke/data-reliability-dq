# Greenplum / MPP: что важно для DQ-проверок

Памятка по решениям, которые влияют на стоимость и корректность проверок.
Относится к Greenplum 6/7; отличия от ClickHouse отмечены отдельно.

## 1. Распределение определяет стоимость запроса

`DISTRIBUTED BY (account_id)` для оборотов выбран не «по счёту вообще», а под
конкретные запросы:

- `LAG(balance_eod) OVER (PARTITION BY account_id, currency ORDER BY dt)` —
  окно считается локально на сегменте, потому что все строки одного счёта
  лежат на одном сегменте;
- отчёт «по счёту за период» читает один сегмент, а не все.

Если распределить по `dt` (что кажется логичным для партиционированной по дате
таблицы), каждая оконная проверка получит Redistribute Motion по `account_id` —
на 500M строк это десятки минут и полная загрузка интерконнекта.

Справочники (`dim_client`, `dim_product`) — `DISTRIBUTED REPLICATED`: их
размер в мегабайтах, а `JOIN` к факту тогда не требует Broadcast и работает
одинаково для любого распределения факта.

## 2. Проверка перекоса (skew)

Перекос — типовая причина «одна проверка идёт 2 минуты, другая 40». Ключ с
несколькими значениями-гигантами (например, `client_id` крупнейшего клиента)
сваливает 30% строк на один сегмент.

```sql
SELECT skcnamespace::text || '.' || skcrelname AS table, skccoeff
  FROM gp_toolkit.gp_skew_coefficients
 WHERE skccoeff > 1.4
 ORDER BY skccoeff DESC;
```

Порог 1.4 — практическое правило: до 1.2 перекос не влияет, выше 1.5 запросы
начинают упираться в самый медленный сегмент. В проекте это проверка №11 в
`sql/greenplum/03_checks.sql` — она относится к «мониторингу производительности
инструментов», а не к качеству данных.

## 3. Партиционирование и pruning

`PARTITION BY RANGE (dt)` помесячно. Любая DQ-проверка обязана содержать
предикат по `dt` (или `month`) — иначе планировщик читает все партиции, включая
архивные. Проверка этого требования — `EXPLAIN`:

```
Partition Selector for mart.fct_account_turnover_daily_1_prt_...
  (dynamic scan id 1) (segments: 8/8)
```

Если в плане видно `Partitions scanned: 36` — предикат не применился
(например, функция от колонки: `date_trunc('day', dt) = ...`).

Правило: `dt >= :window_start AND dt < :window_end` вместо `dt BETWEEN` с
вычислениями над колонкой.

## 4. Стоимость типовых операций

| Операция | Стоимость на MPP | Комментарий |
| --- | --- | --- |
| `COUNT(*)` по партиции | дешёвая | метаданные + локальные счётчики |
| `COUNT(DISTINCT col)` | дорогая | Redistribute Motion по `col`; на 500M строк — часы |
| `GROUP BY` по ключу распределения | дешёвая | локально на сегменте |
| `GROUP BY` по другому ключу | средняя | Redistribute или Broadcast |
| оконная функция с `PARTITION BY` ключа распределения | дешёвая | локальные окна |
| оконная функция с `PARTITION BY` другого ключа | очень дорогая | пересортировка через интерконнект |
| `LEFT JOIN` факт-факт по разным ключам | очень дорогая | Broadcast большой таблицы |

Практический вывод для каталога: у нас нет `COUNT(DISTINCT)` в проверках —
там, где он был бы нужен (уникальность клиентов с оборотами), проверка
переписана на `GROUP BY ... HAVING` по ключу распределения.

## 5. Append-only, column-oriented, сжатие

Факты созданы как `appendonly=true, orientation=column, compresstype=zstd`.
Следствия:

- `UPDATE`/`DELETE` не удаляют строки физически, а пишут в отдельный блок;
  после массовых правок нужен `REORGANIZE` (не `VACUUM` — он для heap-таблиц);
- колоночное хранение ускоряет агрегаты по 2-3 колонкам (`balance_eod`,
  `debit_turnover`) в разы, но `SELECT *` по широкой таблице — медленнее;
- `zstd` уровня 3-4 — компромисс: уровень 9 ускоряет чтение, но загрузка
  становится дороже (важно для ночного окна).

## 6. ANALYZE, а не «оно само»

После загрузки партиции статистика устаревает, планировщик выбирает
`Nested Loop` вместо `Hash Join` и запрос «встаёт». В DAG это отдельная таска
после `publish_mart`; без неё DQ-проверки сами становятся источником инцидентов
по производительности.

```sql
ANALYZE mart.fct_account_turnover_daily;
```

Для партиционированных таблиц — `ANALYZE ROOTPARTITION` на GP 6+, чтобы
статистика собиралась по родителю.

## 7. Ресурсные очереди

Тяжёлая DQ-сверка, запущенная в общей очереди, вытесняет продовые отчёты.
Правило: DQ-проверки идут в отдельной очереди (`gp_resqueue`) с ограничением
`ACTIVE_STATEMENTS`, чтобы мониторинг не мог уронить потребителей. Это же
требование к backfill-задачам.

## 8. Чем ClickHouse отличается (для второго продукта)

| Аспект | Greenplum | ClickHouse |
| --- | --- | --- |
| Распределение | явный ключ `DISTRIBUTED BY` | `ORDER BY` (сортировочный ключ) + шардирование |
| Дубликаты | возможны при `INSERT` без merge | `ReplacingMergeTree` схлопывает асинхронно |
| Оконные функции | полноценные, но дорогие при неверном ключе | поддерживаются, но `FINAL`/`GROUP BY` предпочтительнее |
| Обновление строк | `UPDATE` в AO/`REORGANIZE` | `ALTER ... UPDATE` — тяжёлая мутация |
| Свежесть | `MAX(load_dt)` по метаданным | `system.parts`/`max(modification_time)` |

Проверки DQ в проекте написаны так, чтобы переноситься: метрика — число,
источник — `ops.etl_batch` (а не системный каталог), диалектные различия
изолированы в `db.compile_sql`.

## 9. Что смотреть при инциденте «проверка идёт слишком долго»

1. `pg_stat_activity` — есть ли ожидание на `wait_event_type = 'lock'`
   (проверка ждёт чужой `ALTER TABLE`).
2. `EXPLAIN ANALYZE` — сколько времени в `Redistribute Motion`.
3. `gp_toolkit.gp_skew_coefficients` — не вырос ли перекос после загрузки.
4. `gp_toolkit.__gp_aocsseg` / `pg_relation_size` — не раздуло ли таблицу
   после серии `UPDATE` (нужен `REORGANIZE`).
5. Статистика: `ANALYZE` выполнялся после последней загрузки?
