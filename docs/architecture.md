# Архитектура и принятые решения

## 1. Контекст

Аналитическое хранилище по ключевым клиентам банка (юрлица) агрегирует данные из
АБС, CRM и продуктовых витрин, а поверх него строятся аналитические отчёты и
дашборды. Потребители — аналитики, продуктовые команды, риск. Контур сопровождения
отвечает за два вопроса:

1. **Данные корректны?** (Data Quality)
2. **Хранилище доступно и укладывается в сроки?** (Data Reliability / SLA)

Оба вопроса ранее закрывались «глазами аналитика»: если дашборд выглядел странно,
писали в чат. Стоимость ошибки: решение по клиенту принимается по завышенному
обороту или по неполному портфелю, а обнаружение происходит через день.

## 2. Слои

| Слой | Ответственность | Где |
| --- | --- | --- |
| Сбор | загрузка из источников, запись `ops.etl_batch` | внешние DAG'и (в проекте — контракт таблицы) |
| `mart` | dim/fct для отчётов | `sql/greenplum/01_mart_ddl.sql` |
| DQ-движок | прогон каталога, пороги, статусы | `src/reliability/checks.py` |
| Реестр состояния | результаты прогонов и инциденты | `src/reliability/store.py`, `incidents.py` |
| Экспозиция | отчёт md, Prometheus, вебхук | `report.py`, `metrics.py`, `notifications.jsonl` |
| Оркестрация | расписание, ретраи, SLA, эскалация | `dags/` |

Слой `ops` намеренно отделён от `mart`: DQ-метаданные не должны переезжать при
перестройке витрин и не должны читаться из тех же партиций, которые проверяются.

## 3. Почему проверка возвращает число, а не boolean

Проверка вида «есть ли дубликаты» даёт ответ «да/нет» и ноль информации о тренде.
Проверка-метрика даёт:

- сравнение с порогом без изменения SQL (порог — данные, а не код);
- зону `warn` (деградация) отдельно от `fail` (инцидент);
- историю в `ops.dq_result` и график в Prometheus;
- единый контракт для SQL-проверок и Python-валидаторов.

Контракт: запрос возвращает **одну строку** с колонкой `metric_value` и, опционально,
`rows_examined` и `message`. Пороги задаются в каталоге:

```json
"bounds": { "fail": { "max": 0.05 }, "warn": { "max": 0.02 } }
```

`max` — «значение не должно превышать» (ошибки, дубликаты, часы отставания),
`min` — «значение не должно быть меньше» (доля валидных ИНН, коэффициент объёма).

## 4. Дорогие проверки не должны мешать дешёвым

Стоимость проверок различается на порядки:

| Класс | Пример | Стоимость на 500M строк |
| --- | --- | --- |
| метаданные | `ops.etl_batch MAX(load_dt)` | миллисекунды |
| агрегат по партиции | дубликаты за 7 дней | секунды-десятки секунд |
| окно по всей истории | непрерывность остатка за 30 дней | десятки секунд (партиции + распределение по `account_id`) |
| сверка факт-факт | rowcount против источника | минуты, отдельный пул |

Правило: проверка никогда не читает больше, чем нужно для ответа, и всегда имеет
предикат по партиционирующему ключу. Тяжёлые сверки выносятся в отдельный пул
Airflow и запускаются реже (раз в сутки), а не в 30-минутный цикл.

## 5. Дедупликация инцидентов

Одна сломанная партиция ломает одну проверку на каждом прогоне. Без дедупликации
дежурный получает поток однотипных тикетов и перестаёт их читать (alert fatigue) —
это худший из возможных исходов мониторинга. Поэтому:

- ключ дедупликации `check_id|entity`;
- повторный `FAIL` увеличивает `occurrences` и `last_seen_at`;
- новый инцидент открывается только после закрытия предыдущего;
- `PASS` закрывает инцидент автоматически и пишет `run_id` в `resolution_note`,
  чтобы в постмортеме было видно, какой прогон подтвердил восстановление.

Альтернатива — «всегда новый тикет» — удобна для аудита, но непригодна для
дежурства. Компромисс: полная история прогонов остаётся в `ops.dq_result`,
агрегированная — в инцидентах.

## 6. Диалект SQL

Прод — Greenplum (PostgreSQL), демо — SQLite. Различия изолированы в
`db.Database.compile_sql`:

- макрос `{{ age_hours('load_dt') }}` разворачивается в `julianday(...)` или
  `EXTRACT(EPOCH FROM ...)`;
- плейсхолдеры `:name` конвертируются в `%(name)s` для psycopg2.

Правила для авторов проверок: только `CAST(x AS type)`, без `::`; без
`schema.table` в демо-каталоге (прод-редакция лежит в `sql/greenplum/`).

Почему не ORM и не фреймворк: проверки пишут аналитики и DRE, SQL должен
оставаться SQL, а не строиться из DSL. JSON-каталог версионируется в Git и
проходит ревью как код.

## 7. SLA и SLO

| Сущность | SLA свежести | Деградация (`warn`) |
| --- | --- | --- |
| `fct_account_turnover_daily` | 26 ч | 21 ч |
| `fct_loan_portfolio_monthly` | 24 ч | 20 ч |

26 часов для оборотов — это ночная загрузка плюс буфер на перезапуск: если
поставить ровно 24, любой retry ночного DAG'а превращается в ложный инцидент.

SLO контура: 99.5% суток в месяце mart готов к 08:30 (бюджет ошибки ≈ 2 часа в
месяц). Метрика считается в `dags/mart_freshness_sla_dag.py` и публикуется в тот
же дашборд, что и DQ-метрики.

## 8. Что сознательно не сделано

- **Нет автолечения.** Автоматический перезапуск загрузки при `FAIL` опасен:
  часть дефектов (долг выше лимита, дубликаты) не лечится повтором ETL, а
  повторный прогон поверх грязной партиции усугубляет проблему.
- **Нет проверок «на всё».** 12 проверок покрывают гранулярность, полноту,
  целостность, свежесть, объём и один бизнес-инвариант. Увеличение каталога без
  роста числа найденных инцидентов — это стоимость без ценности.
- **Нет хранения сэмплов строк в полном объёме.** Хранятся первые 5 строк
  нарушения: достаточно для воспроизведения, не раздувает `ops`-схему.

## 9. Развитие

1. Профилирование колонок (min/max/уникальность/распределение) с автоматическим
   предложением порогов вместо ручных.
2. Anomaly detection на исторических метриках (`ops.dq_result`) — сезонность
   объёмов в конце месяца и в дни закрытия отчётности.
3. Матрица lineage: какая проверка защищает какой отчёт и какие дашборды
   затрагивает инцидент (ответ на вопрос «а это точно влияет на бизнес?»).
4. DQ-гейт в релизном процессе: PR в mart-слой не мержится без прогона каталога
   на тестовой партиции.
