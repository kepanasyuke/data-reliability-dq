# Каталог DQ-проверок: что и почему проверяем

Документ отвечает на вопрос «почему эта проверка вообще нужна» — то, что в
Confluence обычно пишут один раз, а потом никто не обновляет. Здесь каждая
проверка привязана к бизнес-метрике, которую она защищает.

## Как читать таблицы

- **Grain** — что означает одна строка таблицы. Нарушение grain ломает все
  агрегаты выше.
- **Дефект** — как выглядит ошибка в данных.
- **Что видит потребитель**, если проверки нет.
- **Порог** — `fail` / `warn`.

## Обороты и остатки по расчётным счетам

Таблица: `mart.fct_account_turnover_daily`
Grain: `account_id + dt + currency`. Потребители — отчёты по оборотам, рейтинги
клиентов, дашборды РКО, расчёт среднемесячных остатков.

| Проверка | Дефект | Что видит потребитель без проверки | Порог |
| --- | --- | --- | --- |
| `turnover.freshness` | загрузка не приехала или упала | «пустой» вчерашний день, дашборд показывает падение бизнеса | fail > 26 ч, warn > 21 ч |
| `turnover.duplicate_grain` | повторная вставка партиции без merge | обороты и остатки завышены в 2 раза | fail > 0 |
| `turnover.orphan_client` | клиент удалён/не приехал в справочник | строка есть, но в отчётах по клиентам её нет — потеря выручки | fail > 0 |
| `turnover.balance_non_negative` | ошибка знака, неучтённый овердрафт | отрицательный остаток в отчёте, некорректный лимит риска | fail > 0 |
| `turnover.balance_continuity` | пропущен день, задвоена строка, сдвиг остатка | «тихое» расхождение: остаток не сходится с оборотами, но каждая строка валидна по отдельности | fail > 0 |
| `turnover.volume_anomaly` | частичная загрузка (упал источник, обрезался файл) | свежесть в норме, а данные за день есть на 40% счетов | fail < 0.7, warn < 0.85 |

Почему непрерывность остатка — отдельная проверка: это единственный инвариант,
связывающий строки между собой. Проверки «нет дублей» и «нет пропусков» по
отдельности пропускают сценарий «день приехал, но остаток пересчитан по другому
курсу/валюте».

## Кредитный портфель

Таблица: `mart.fct_loan_portfolio_monthly`
Grain: `client_id + product_code + month`. Потребители — отчёты по портфелю,
просрочке, лимитам, риск-дашборды.

| Проверка | Дефект | Что видит потребитель без проверки | Порог |
| --- | --- | --- | --- |
| `loans.freshness` | месячная загрузка отстала больше суток | устаревший портфель в утреннем отчёте | fail > 24 ч, warn > 20 ч |
| `loans.debt_within_limit` | долг больше одобренного лимита | завышенная утилизация лимитов, ошибка в расчёте кредитного риска | fail > 0 |

`debt_within_limit` — пример бизнес-инварианта, который нельзя выразить
техническими проверками: с точки зрения схемы всё валидно, а с точки зрения
банка — нет. Такие правила приносят аналитики продукта, DRE их формализует.

## Справочник клиентов

Таблица: `mart.dim_client`. Потребители — все отчёты по клиентам, сопоставление
с внешними источниками (ФНС, рейтинги, скоринг).

| Проверка | Дефект | Что видит потребитель без проверки | Порог |
| --- | --- | --- | --- |
| `client.inn.valid` | контрольное число не сходится (или не тот формат: 10 знаков у ЮЛ, 12 у ИП) | клиент не матчится с отчётностью, дубли клиентов в аналитике | fail < 0.995, warn < 1.0 |
| `client.ogrn.valid` | сломана контрольная цифра ОГРН/ОГРНИП | неверная связка с ЕГРЮЛ, ошибки в юридических выгрузках | fail < 0.995, warn < 1.0 |
| `client.segment.completeness` | сегмент не заполнен | клиент выпадает из разреза «по сегментам», суммы в дашборде не бьются с итогом | fail > 5%, warn > 2% |

Проверка контрольных чисел реализована в Python (`validators.py`), потому что в
SQL это превращается в неподдерживаемую конструкцию из `SUBSTR` и арифметики,
а тестировать её надо юнит-тестами на реальных ИНН.

## Метаданные загрузок

Таблица: `ops.etl_batch`.

| Проверка | Дефект | Что видит потребитель без проверки | Порог |
| --- | --- | --- | --- |
| `batch.rowcount_match` | ETL отчитался об успехе, но строк приехало меньше/больше | «успешная» загрузка с потерей данных, обнаруживается через недели | fail > 0, warn > 50 |

## Как добавить проверку

1. Сформулировать бизнес-инвариант: что именно станет неверным в отчёте.
2. Написать запрос, возвращающий одну строку `metric_value` (и, если полезно,
   `rows_examined`). Предикат по ключу партиционирования обязателен.
3. Добавить `sample_sql` — 5 строк нарушения, чтобы дежурный сразу видел, что
   именно сломалось, без похода в кластер.
4. Задать `bounds.fail` (и `bounds.warn`, если деградация отличается от аварии).
5. Прогнать `python run.py seed && python run.py run` — убедиться, что проверка
   зеленеет на чистых данных (ложных срабатываний нет).
6. Внести проверку в `docs/dq-checks.md` и поднять `version` каталога.

Пример:

```json
{
  "check_id": "turnover.currency_in_domain",
  "title": "Валюта счёта в справочнике валют",
  "entity": "fct_account_turnover_daily",
  "severity": "P3",
  "unit": "count",
  "bounds": { "fail": { "max": 0 } },
  "sql": "SELECT COUNT(*) AS metric_value FROM fct_account_turnover_daily WHERE dt >= :window_start AND currency NOT IN ('RUB','USD','EUR','CNY')",
  "sample_sql": "SELECT account_id, dt, currency FROM fct_account_turnover_daily WHERE dt >= :window_start AND currency NOT IN ('RUB','USD','EUR','CNY') LIMIT 5"
}
```

## Severity: как выбирать

- **P1** — данные в дашборде уже неверны или отсутствуют; решение по клиенту
  может быть принято на основе ошибки. Реакция — немедленно, эскалация дежурному.
- **P2** — часть разрезов искажена, либо метрика деградирует; до утреннего
  отчёта есть время. Реакция — в течение часа, в рабочие часы.
- **P3** — техническое расхождение без влияния на бизнес-числа (метаданные,
  служебные атрибуты). Реакция — в течение дня.
